# Design

## Context

Проект пустой: есть только `PRODUCT.md`, `HOSTING.md` и OpenSpec. Зачем это
нужно и что входит в объём — см. `proposal.md`; требования — в `specs/`.

Ограничения, определяющие подход:

- Боевой хостинг в РФ (152-ФЗ), прототип показывается бесплатно — локально
  или на VPS с пробным грантом облака. Провайдер пока не выбран.
- Каталог на сотни позиций ведёт заказчик-нетехнарь, ему нужна готовая
  удобная админка на русском.
- Один сервер, низкая нагрузка: оптовый B2B-сайт, десятки заявок в день в
  лучшем случае.

Проверенные версии на 8 ноября 2026: `payload` 3.93.0 (стабильная, v4 — в
бете), `next` 16.4.5; `@payloadcms/next` 3.93 поддерживает Next.js
`>=16.3.3 <17`. Локально есть Node 26, Docker 29, Docker Compose 5, pnpm 12.

## Goals / Non-Goals

**Goals:**

- Один репозиторий и один процесс: публичный сайт и админка в одном
  приложении Next.js.
- Одинаковый запуск локально, на демо-VPS и на боевом VPS: `docker compose up`
  и файл `.env`.
- Код, который можно развивать до боевой версии без переписывания.

**Non-Goals:**

- Финальный визуальный дизайн: прототип чистый и аккуратный, но фирменный
  стиль — отдельной задачей.
- Горизонтальное масштабирование, CDN, очереди.
- Автоматизация развёртывания (CI/CD) и выбор провайдера VPS.

## Decisions

### 1. Next.js 16 + Payload CMS 3.x в одном приложении

Payload встраивается в Next.js (маршруты `/admin` и `/api` в группе
`(payload)`, сайт — в группе `(frontend)`). Он даёт админку, авторизацию,
загрузку файлов, валидацию и Local API для серверных компонентов.

- *Своя админка* — недели работы на то, что Payload даёт готовым.
- *Strapi / Directus* — отдельный сервис рядом с фронтендом: два процесса и
  два деплоя вместо одного.
- *Payload 4 beta* — нестабильный API. Берём 3.93, на v4 переходим отдельным
  change после релиза (есть codemod).

### 2. PostgreSQL через `@payloadcms/db-postgres`

В разработке схема синхронизируется автоматически (`push`), для боевой версии
и демо-VPS миграции генерируются и коммитятся в `src/migrations/`, а
применяются при старте контейнера (`payload migrate`).

- *SQLite* проще, но хуже переносится на управляемые базы и S3-окружения.
- *MongoDB* — нет смысла: данные реляционные (товары, категории, заявки).

### 3. Модель данных

```
 Коллекции                                          Глобальные настройки
 +-------------+  +-------------------------------+  +---------------------+
 | users       |  | products                      |  | site-settings       |
 |  auth, 1 шт |  |  name*, slug (уник., авто)    |  |  companyName, phone,|
 +-------------+  |  sku, altNames, formula, cas, |  |  email, address,    |
 | categories  |<-|  gost, tu, packaging,         |  |  inn, ogrn, kpp,    |
 |  name, slug,|  |  availability: stock|order,   |  |  legalAddress,      |
 |  order      |  |  categories[] (many),         |  |  requestEmails[]    |
 +-------------+  |  description, application,    |  +---------------------+
 | media       |<-|  storage, transport, safety   |  | about-page          |
 |  image/*    |  |   (rich text),                |  | privacy-policy      |
 |  <= 10 МБ   |  |  specs[] {name, value},       |  | pd-consent          |
 +-------------+  |  gallery[] -> media,          |  |  (rich text, флаг   |
 | documents   |<-|  documents[] -> documents,    |  |   "черновик")       |
 |  pdf/doc/xls|  |  published (bool)             |  +---------------------+
 |  <= 20 МБ,  |  +-------------------------------+
 |  title      |  | requests (только чтение)      |
 +-------------+  |  name, phone, email, message, |
                  |  items[] {product?, name, sku,|
                  |   quantity}, source,          |
                  |  consentAt, ip, createdAt     |
                  +-------------------------------+
```

- **Публикация** — булево поле `published`, а не черновики Payload (`drafts`).
  Черновики добавляют версии и путают нетехнического пользователя. Нам нужно
  только «показывать / не показывать».
- **Снимок позиций в заявке**: `items[]` хранит `name` и `sku` на момент
  отправки и необязательную ссылку на товар. Удаление товара обнуляет ссылку,
  но заявка остаётся читаемой.
- **Фото и документы — две разные upload-коллекции**: у них разные типы,
  лимиты размера и обработка (для фото — ресайз через `sharp`).
- **Длинные тексты** — rich text на Lexical, короткие поля — `text`.
- **Адрес карточки**: `slug` формируется в хуке `beforeValidate` транслитом
  названия (своя функция по таблице ГОСТ 7.79, без зависимостей), при
  совпадении добавляется суффикс `-2`, `-3`.
- **Один администратор**: у `users` `access.create` всегда `false`, учётная
  запись создаётся сидом из `ADMIN_EMAIL` и `ADMIN_PASSWORD` через Local API с
  `overrideAccess`. Сброс пароля — штатный механизм Payload через SMTP.
- **Админка на русском**: `i18n` с языком `ru` по умолчанию, подписи
  коллекций и полей заданы по-русски.

### 4. Хранение файлов: диск по умолчанию, S3 опционально

Upload-коллекции пишут на диск в смонтированный том (`/app/uploads`). Если
задан `S3_BUCKET`, в конфиге подключается `@payloadcms/storage-s3` (ключ
`storage`) для Yandex Object Storage или Selectel без изменений кода.

- *Только S3* — лишний платный сервис для прототипа.
- *Только диск* — закрывает путь к хранилищу при росте; адаптер подключается
  одной условной строкой.

### 5. Приём заявки: Server Action → Local API

```
 браузер                       сервер Next.js                    внешнее
 +----------------+  action   +-------------------------------+
 | форма заявки   |---------->| 1. ловушка, время, лимит IP   |
 | + список       |           | 2. валидация (zod)            |
 |   запроса из   |           | 3. снимок позиций: проверить, |
 |   localStorage |           |    что товары опубликованы    |
 +----------------+           | 4. payload.create(requests)   |
        ^                     |    hook afterChange(create):  |  SMTP
        |  ok / ошибки полей  |      письмо, try/catch -------+------>
        +---------------------| 5. ответ                      |
                              +-------------------------------+
```

- Через REST коллекция `requests` недоступна для создания (`access.create`
  только для авторизованного пользователя); сайт создаёт заявки через Local
  API с `overrideAccess: true` после своих проверок. Так антиспам нельзя
  обойти прямым запросом к `/api/requests`.
- Одна и та же схема zod проверяет поля и на клиенте (подсказки у полей), и
  на сервере (источник истины).
- **Письмо — в хуке `afterChange`** коллекции `requests`, вызывается с
  `await` внутри `try/catch` и с таймаутом SMTP. Ошибка пишется в лог и не
  отменяет сохранение. Письму ставится `replyTo` = email посетителя.
  - *Очередь заданий Payload* надёжнее, но требует запуска обработчика и
    ничего не даёт при десятках заявок в день; вернёмся к ней, если письма
    начнут теряться.
- Адресаты — `site-settings.requestEmails`, при пустом списке —
  `REQUESTS_FALLBACK_EMAIL` из окружения.

### 6. Антиспам без внешних сервисов

Скрытое поле-ловушка, отметка времени открытия формы (отправка быстрее
3 секунд отклоняется) и ограничение 5 заявок с IP за 10 минут в памяти
процесса (скользящее окно). IP берётся из `X-Forwarded-For` только от
доверенного обратного прокси.

- *Яндекс SmartCaptcha* — лишнее трение для покупателя и внешний сервис;
  подключаем, если спам пробьётся.
- Лимит в памяти сбрасывается при перезапуске и не работает на нескольких
  экземплярах — для одного сервера это приемлемо.

### 7. Список запроса — в `localStorage`

Клиентское хранилище (React context поверх `useSyncExternalStore`) держит
`{productId, quantity}[]`. При открытии страницы списка сервер возвращает
актуальные данные по этим id, и позиции, которых больше нет на сайте,
удаляются с пояснением. Корзина в базе не нужна: нет логина и оплаты.

### 8. Рендеринг каталога

Серверные компоненты читают данные через Local API. Страницы каталога и
товара рендерятся динамически при каждом запросе: при сотнях позиций и
низкой нагрузке кэш и его инвалидация не окупаются, зато изменения из
админки видны сразу.

- Поиск — `where.or` с `like` (ILIKE в Postgres) по `name`, `altNames`,
  `formula`, `cas`, `sku`; фильтры — `and` по `categories` и `availability`;
  `limit: 24`, `page` из адреса. Для сотен строк индекс не нужен; при росте
  до десятков тысяч — `pg_trgm`.
- Пустые категории скрываются по списку категорий опубликованных товаров
  (один запрос с `select`).
- Карта сайта — `app/sitemap.ts`, метаданные — `generateMetadata`.

### 9. Интерфейс

Tailwind CSS 4 и небольшой набор своих компонентов (кнопка, поле, модальное
окно, карточка). Визуальное направление — сдержанный «промышленный»
B2B-стиль, не копия ldhim.ru; финальная полировка — отдельно.

- *shadcn/ui* — удобно, но для десятка компонентов лишний слой; можно
  добавить позже.

### 10. Демо-данные

Скрипт `pnpm seed` (`payload run src/seed/index.ts`) создаёт администратора,
настройки сайта, 6 категорий, 25 товаров с заполненными полями, черновики
юридических страниц и образец PDF-документа у нескольких товаров. Повторный
запуск пропускает существующие записи; `--reset` очищает каталог.

Картинки-заглушки скачиваются с placehold.co один раз при разработке (PNG
800×600 с латинской подписью, например, артикулом) и коммитятся в
`src/seed/assets/`. Так сид работает без интернета, а товары устроены так же,
как настоящие.

Предполагаемые категории (заказчик уточнит позже): «Кислоты», «Щёлочи и
соли», «Растворители», «ПАВ», «Гликоли и спирты», «Сорбенты и
катализаторы».

### 11. Контейнеры и окружение

```
 docker-compose.yml
 +-----------+     +-------------+     +-------------------------------+
 | app       |---->| postgres:17 |     | mailpit (профиль dev)         |
 | Next.js   |     | том db-data |     | SMTP :1025, UI :8025 только   |
 | standalone|     +-------------+     | на 127.0.0.1                  |
 | том       |                         +-------------------------------+
 | uploads   |---- SMTP ------------> mailpit (dev) или реальный SMTP
 +-----------+
 перед app на VPS: Caddy (профиль proxy) — HTTPS по DOMAIN
```

- `Dockerfile` — многоэтапная сборка, `output: 'standalone'`, образ на
  актуальной LTS Node. При старте `payload migrate`, затем сервер.
- Переменные окружения (`.env.example`): `DATABASE_URL`, `PAYLOAD_SECRET`,
  `NEXT_PUBLIC_SERVER_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
  `SMTP_PASS`, `SMTP_FROM`, `REQUESTS_FALLBACK_EMAIL`, `ADMIN_EMAIL`,
  `ADMIN_PASSWORD`, необязательные `S3_*` и `DOMAIN`.
- Mailpit ловит письма в разработке и на демо — заказчик видит, как
  выглядит письмо о заявке, без настройки настоящей почты.

### 12. Тестирование

- **Vitest, модульные тесты**: транслит и уникальность адреса, схема
  валидации заявки, лимитер, проверки антиспама, формирование письма.
- **Vitest, интеграционные тесты** с Postgres из Docker: создание заявки
  через Local API, хук письма с подменённым транспортом (письмо отправлено;
  при сбое SMTP заявка сохранена), права доступа к `requests` и `users`.
- **Playwright**: сквозные сценарии на поднятом стеке — поиск и фильтры,
  карточка и скачивание документа, список запроса и отправка заявки (письмо
  проверяется через API Mailpit), создание и снятие с публикации товара в
  админке.

## Risks / Trade-offs

- [Payload 4 выйдет и изменит API] → Фиксируем 3.93.x, переход — отдельный
  change с codemod; бизнес-логика вынесена из конфига в `src/lib`.
- [Письмо в синхронном хуке задерживает ответ на время SMTP] → Таймаут
  транспорта 10 секунд; при проблемах — перенос в очередь заданий Payload.
- [Письма уходят в спам] → Отправка с ящика на домене заказчика с SPF и DKIM;
  заявки в любом случае сохраняются в админке.
- [Файлы на диске теряются вместе с VPS] → Том `uploads` входит в бэкап
  вместе с дампом базы; переход на S3 без изменения кода (решение 4).
- [Лимит в памяти обходится сменой IP или сбрасывается рестартом] → Для
  прототипа достаточно; запасной вариант — SmartCaptcha.
- [Payload и Next.js требовательны к памяти на дешёвом VPS] → Образ
  собирается локально и загружается в реестр; на VPS только запуск. Нужно
  не меньше 2 ГБ ОЗУ.
- [`push`-схема в разработке расходится с миграциями] → Миграция
  генерируется и коммитится в конце каждой задачи, меняющей коллекции.

## Migration Plan

Существующей системы нет. Развёртывание прототипа:

1. Локально: `cp .env.example .env`, `docker compose --profile dev up -d`,
   `pnpm seed`.
2. На демо-VPS: собрать и загрузить образ, скопировать `docker-compose.yml`
   и `.env`, `docker compose --profile proxy up -d`, выполнить сид в
   контейнере.
3. Откат: предыдущий тег образа и восстановление дампа Postgres и тома
   `uploads`.

## Open Questions

Не влияют на подход и разбивку задач, уточняются у заказчика по ходу:

- Окончательный список категорий: в сиде используются предполагаемые.
- Адрес (или адреса) для заявок: задаётся в настройках сайта.
- Тексты политики конфиденциальности и согласия: до получения — черновики.
- Домен и провайдер VPS: на код не влияют, только на `.env` и `DOMAIN`.
